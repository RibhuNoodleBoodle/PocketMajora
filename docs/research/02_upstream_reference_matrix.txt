* How 2S2H Modifies Vanilla `zeldaret/mm` Game Code (`mm/src/`):
  1. Symbolic Asset Strings (`__OTR__`):
     - `mm/assets/**/*.h` defines 24,918 `__OTR__<path>` string literals in place of N64 segmented pointers or raw C arrays.
     - Game code passes pointers (which may be either N64 segmented addresses or `"__OTR__..."` strings) into `ResourceMgr_OTRSigCheck(ptr)` and `ResourceMgr_Load*ByName(...)` (161 direct call sites in `mm/src/`, plus renderer/scene interceptors in `z_play_2SH.cpp`, `z_scene_2SH.cpp`, and `libultraship`'s `Fast3d` interpreter).
  2. Flattened Single-Thread Coroutine Loop (`mm/src/code/graph.c`):
     - Unlike N64 multi-threaded `irqmgr`/`scheduler`/`graph`, 2S2H flattens frame execution into `RunFrame()` (`graph.c:371-427`), stepping `PadMgr_ThreadEntry(&gPadMgr)` -> `Graph_Update(&gfxCtx, gameState)` -> `Graph_UpdateGame` (`Audio_Update`) -> `Graph_ExecuteAndDraw` (`GameState_Update` + `Graph_ProcessGfxCommands`).
     - This cooperative single-frame state machine (`runFrameContext`) is directly amenable to a Rust main loop on PSP.
  3. Stubbed N64 DMA (`mm/src/boot/z_std_dma.c`):
     - `DmaMgr_DmaRomToRam` and `DmaMgr_ProcessMsg` are `#if 0`'d out because 2S2H loads scenes, rooms, skeletons, animations, textures, display lists, and text via `ResourceMgr_*` from `.o2r` (ZIP) / `.otr` (MPQ) archives.
  4. Heavy Desktop Runtime Coupling in `2s2h/` + `libultraship`:
     - `libultraship` + `2s2h/` depend on C++20 STL, `spdlog`, `nlohmann::json`, `tinyxml2`, `libzip`, `StormLib` (MPQ), `SDL2`, `OpenGL/Metal/DX11`, `ImGui`, and unbounded heap allocations (hundreds of megabytes on PC). None of that C++ desktop stack can run within PSP-3000's 64 MiB physical RAM or `mipsel-sony-psp`.

3. PSP REFERENCE PORT ANALYSIS (`psp_ref/` -- `z2442/mm-PSP` & `z2442/oot-PSP`)
----------------------------------------------------------------------
* Reference Identity & Provenance:
  - Repository: `https://github.com/z2442/mm-PSP` (local snapshot at `psp_ref/`)
  - Shared Backend: `https://github.com/z2442/oot-PSP` at commit `d4ad96c045d39e18a80f7a1f5d7f8fdba9621d38` (Nov 10, 2026)
  - Base Upstream: Fork of `zeldaret/oot` & `zeldaret/mm` decompilations (C99 + MIPS Allegrex assembly)
  - License Status of `psp_ref/`:
    * `psp_ref/docs/PSPSDK-LICENSE.txt` is BSD-3-Clause; `psp_ref/tools/ZAPD/LICENSE` is MIT; `fado`, `asm-differ`, `asm-processor` are MIT/Unlicense.
    * IMPORTANT: Neither `z2442/mm-PSP` nor `z2442/oot-PSP` includes a top-level permissive open-source license file covering `src/port/psp/**`.
    * Legal Rule: Treat `psp_ref/src/port/psp/**` strictly as a clean-room technical reference for hardware behavior, memory budgets, and RSP/RDP/GU edge cases. DO NOT copy C/ASM source lines from `psp_ref/src/port/psp/**` into our Rust codebase.

* Technique-by-Technique Evaluation from `psp_ref/`:

  1) Memory Partitioning & 64 MiB Slim Budget (`psp_ref/src/port/psp/mm_psp_game.c:795-936`, `docs/psp-port.md:9-14`)
     - Mechanism: Requests `MEMSIZE=1` in `PARAM.SFO`. Keeps default libc heap small (~1 MiB) and allocates dedicated Partition 2 (`PSP_MEMORY_PARTITION_USER`) blocks via `sceKernelAllocPartitionMemory`:
       * 8 MiB game arena (`MM_PSP_SYSTEM_HEAP_SIZE`)
       * Up to 8 permanent renderer blocks (`MmPspRenderer_Memalign`: ~816 KiB in LCD mode)
       * Up to 16 asset cache blocks (`MmPspAssetCache_Malloc`: including MM's 5.3 MiB `Audiotable` which exceeds PSP's 4 MiB volatile partition)
       * 2 MiB audio external pool
     - Decision: **REIMPLEMENT IN RUST**. `AndrewAltimit/rust-psp` (`e4cc06f6`) already provides an 8 MiB static heap + >=256 KiB kernel block allocator (`src/alloc.rs`). We will build a deterministic Rust slab/block manager on top of `sceKernelAllocPartitionMemory(SceSysMemPartitionId::SceKernelPrimaryUserPartition, ...)` with explicit budgets for Game Arena, Scene/Object Cache, Texture/Mesh Cache, and Audio Pool.

  2) F3DEX2 Display List -> PSP `sceGu` Translation (`psp_ref/src/port/psp/backend/gfx/gfx_fast3d.c`, `gfx_scegu.c`, `mm_psp_gfx_scegu.c`)
     - Mechanism:
       * Translates F3DEX2 matrix stacks, vertex loads (`gSPVertex`), triangles (`gSP1Triangle`/`gSP2Triangles`), and RDP combiner/tile states into PSP GE command lists.
       * Uses a 36-byte native vertex format and caches immutable static display-list meshes in user RAM so static room geometry does not re-decode every frame.
       * Handles MM-specific two-cycle combiner passes, per-tile TLUT palettes, animated water scrolling, and Clock Town 12-bit wrapped tile bounds (`docs/psp-port.md:76-104`).
       * Motion blur uses GPU-owned framebuffer history blended via unlit 32-pixel sprite strips and captured before HUD via `sceGuCopyImage` without CPU readback (`docs/psp-port.md:92-97`).
       * LCD mode uses triple buffering in 2 MiB EDRAM (`480x272`); scene scissor and letterbox bar endpoints use identical rounding to prevent clear-color seams during Z-targeting (`docs/psp-port.md:162-165`).
     - Decision: **REIMPLEMENT IN RUST**. Our Rust renderer crate will consume 2S2H display list resources (F3DEX2 GBI words) and emit `psp::sys::sceGu*` commands using these exact hardware insights (GPU-local motion blur via `sceGuCopyImage`, 12-bit UV wrapping, two-pass combiner fallback, and consistent letterbox scissor rounding).

  3) VFPU Matrix & Clipping Acceleration (`psp_ref/src/port/psp/backend/oot_psp_vfpu_matrix.h`, `gfx/gfx_transform_vfpu.s`, `gfx/gfx_clip_vfpu.s`, `oot_psp_memory.c`)
     - Mechanism: Uses Allegrex VFPU quad-word (`lv.q`/`sv.q`/`ulv.q`, `vmmul.q`, `vtfm4.q`) for 4x4 matrix multiplication, vertex projection/clipping across 6 frustum planes, and 64-byte aligned bulk memory copies.
     - Decision: **REIMPLEMENT IN RUST**. `AndrewAltimit/rust-psp` includes `vfpu_asm!` macro support in Rust; we will write pure-Rust `vfpu_asm!` routines for 4x4 matrix math and frustum clipping after baseline scalar Rust correctness is proven.

  4) First-Boot On-PSP ROM Extraction vs Host Extraction (`psp_ref/src/port/psp/mm_psp_asset_builder.c`, `backend/oot_psp_asset_loader.c`, `backend/oot_psp_runtime_patch.c`)
     - Mechanism: `mm-PSP` links 570k lines of C with zero-initialized asset arrays (`asset_symbols.S`, 4.9 MiB assembly source), reads `data/basrom.z64` (CRC32 `0xB428D8A7`, `dmadata` at `0x1A500` with 1,552 entries) on PSP first boot, decompresses Yaz0 segments, applies byte-swap recipes (`asset_transform.z` + `runtime_patches.z`), and writes `data/segments/oot_psp_assets.bin`.
     - Decision: **ADAPT CONCEPT / REJECT ZERO-ARRAY LINKING**. Linking giant zero-filled static C arrays into the executable is specific to `mm-PSP`'s monolithic C link layout. Instead, following 2S2H's architecture, our Rust port will use a **Host-Side Rust Asset Extractor/Compiler (`tools/pmm-extractor`)** (with optional on-PSP validation) that reads the user's legal US N64 ROM (`CRC32 B428D8A7` / SHA-1 `d6133ace5afaa0882cf214cf88daba39e266c078`) + `majora_code/mm/assets/xml/*.xml` and outputs an untracked, PSP-optimized 2S2H resource pack (`ms0:/PSP/GAME/POCKET_MM/data/pmm_2s2h.pak`) where every `__OTR__*` resource is pre-swapped to little-endian and aligned for zero-copy PSP loading.

  5) Audio Synthesis & Media Engine Offload (`psp_ref/src/port/psp/backend/oot_psp_audio_backend.c`, `oot_psp_mixer.c`, `oot_psp_me_entry.s`)
     - Mechanism: MM synthesizes audio at 32 kHz (`docs/psp-port.md:111`). `mm-PSP` builds ABI audio command lists on the main Allegrex CPU and optionally offloads mixing (`oot_psp_mixer.c`) to the PSP Media Engine (ME) co-processor via a kernel driver, or falls back to Allegrex (`PSP_AUDIO_MEDIA_ENGINE=0`).
     - Decision: **ADAPT (ALLEGREX FIRST, ME OPTIONAL)**. Kernel-mode ME drivers complicate user-mode EBOOT portability across CFW/PPSSPP versions. We will implement the 32 kHz Rust audio mixer on an Allegrex high-priority audio thread first (like `PSP_AUDIO_MEDIA_ENGINE=0`), using VFPU vectorization if needed, keeping ME offload strictly optional for later optimization.

  6) Coordinated Suspend / Resume & Flash Save Timing (`psp_ref/src/port/psp/backend/oot_psp_suspend.c`, `mm_psp_game.c:590-653`)
     - Mechanism:
       * Power callback coordinates sleep: drains GU & audio, closes open `ms0:`/`ef0:` descriptors before suspend, and re-opens the asset pack and restores GU state on resume.
       * Flashrom save emulation (`mm-psp-save.bin`, 128 KiB `0x20000`) reports `SysFlashrom_IsBusy()` until the game state collects `SysFlashrom_AwaitResult()`, preserving MM's two-second save confirmation delay and owl save transitions.
       * Converts PSP RTC microseconds (`sceRtcGetCurrentTick`) into N64 `OS_CPU_COUNTER` units (46.875 MHz) for deterministic deadlines.
     - Decision: **REIMPLEMENT IN RUST**. Both the two-step async flashrom completion contract and the power-callback file-descriptor recovery are critical hardware lessons to implement natively in Rust.

4. EVALUATION OF IMPLEMENTATION ROUTES (ROUTE A vs ROUTE B)
----------------------------------------------------------------------
Per Master Prompt Section D (Stage 2) and Owner Constraint #2 ("Write the PSP runtime/game adaptation MAINLY IN RUST... Never misrepresent C/C++ engine code behind a tiny Rust wrapper as a Rust port"):

* ROUTE A: Pure-Rust 2S2H Architecture & Staged Rust Game Translation (RECOMMENDED PRIMARY ROUTE)
  - Description:
    1. Build 100% of the PSP runtime, OS/kernel layer, memory block allocator, 2S2H resource manager (`__OTR__*` loader), F3DEX2->`sceGu` hardware renderer, 32 kHz audio backend, controller/save subsystem, and `Graph`/`GameState` main loop in **Rust** (`no_std` + `alloc` via `AndrewAltimit/rust-psp`).
    2. Build a **Rust host-side asset compiler (`tools/pmm-extractor`)** that parses `majora_code/mm/assets/xml/*.xml` and the owner's US N64 ROM (`dmadata` + Yaz0) to produce a compact, little-endian, 2S2H-schema binary pack (`pmm_2s2h.pak`) keyed by 2S2H's `__OTR__*` resource paths/hashes.
    3. Translate 2S2H's `mm/src/` and `mm/2s2h/z_*_2SH.cpp` game subsystems into idiomatic Rust crates in vertical slices:
       - Slice 1: Boot, `Graph` frame state machine, `PadMgr`, `SysFlashrom` (128 KiB save), `OTRMessage` text table, and `ResourceMgr` core.
       - Slice 2: F3DEX2 -> `sceGu` renderer + Title Setup / N64 Logo (`ovl_title`) & File Select (`ovl_file_choose`).
       - Slice 3: `PlayState` core (`z_play`, `z_scene`, `z_room`, `z_bgcheck`, `z_camera`, `z_kankyo`, 3-day clock/time cycle, `z_parameter` HUD, `z_player` core) + Clock Town scenes (`SCENE_CLOCKTOWER`, `SCENE_TOWN`, `SCENE_BACKTOWN`, `SCENE_ICHIBA`).
       - Slice 4: Audio synthesis/sequencer + incremental actor overlays.
  - Pros:
    * Zero C/C++ cross-compiler (`psp-gcc`) dependency; builds cleanly and reproducibly with only `cargo-psp` and `rustc` (`nightly-2026-04-13`).
    * Truly honors the owner's Rust-first mandate and keeps memory safety, explicit arena lifetimes, and deterministic PSP RAM budgets under Rust type control.
    * Avoids linking 568k lines of unedited C overlays into PSP RAM at once (which in `mm-PSP` consumes several megabytes of static `.text`/`.data`/`.bss` before dynamic allocation even starts). In Rust, actor/gamestate logic can be modularly organized and data tables loaded on demand from `pmm_2s2h.pak`.
  - Cons / Risks:
    * `majora_code/mm/src/overlays/actors/` contains 635 actors (~429k LOC). Translating every actor in the full game is a multi-stage effort; therefore, vertical-slice milestones (Title -> File Select -> Opening/South Clock Town playable loop with clock cycle) must be strictly scoped and verified step-by-step.

* ROUTE B: Hybrid Rust Runtime + Narrow Temporary C FFI Bridge for Unported `mm/src` Actor/Code Slices (FALLBACK ONLY WITH EXPLICIT OWNER APPROVAL)
  - Description:
    1. Keep the entire PSP platform layer, boot, main loop, memory allocator, 2S2H `ResourceMgr_*` C ABI (`BenPort.h` functions), `sceGu` renderer, audio driver, input, and saves in **Rust**.
    2. Compile selected vanilla C files from `majora_code/mm/src/` with `psp-gcc` into a static archive linked into the Rust crate via `extern "C"`, while Rust implements the `ResourceMgr_*` and `Graph_*` symbols declared in `majora_code/mm/2s2h/BenPort.h`.
  - Cons / Risks:
    * Requires installing a full C `pspdev`/`psp-gcc` toolchain alongside `rust-psp`.
    * `majora_code/mm/src/` has 735 `GameInteractor_*` and 173 `CVar*` calls plus 24,918 `__OTR__` static string literals that bloat `.rodata` in RAM if compiled directly without stripping or macro rewriting.
    * Risks violating Owner Constraint #2 if too much C code is linked behind a Rust shell.
  - Verdict on Route A vs Route B:
    * **Select Route A (Pure-Rust Runtime + Rust Host Asset Compiler + Vertical-Slice Rust Translation of 2S2H Game Subsystems)** as the primary architecture for Stage 3 and Steps 01-10.
    * Keep Route B documented strictly as an optional, owner-gated fallback if later full-game actor coverage requires an automated C->Rust transpiler pass or temporary C ABI shim.
